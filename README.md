白棋在某个局面已有连续冲四取胜（VCF）时，说明上一手黑棋应手不成立：这样的局面不入谱，生成器改选其他黑棋应手。白棋能用挡点反四回应的四三，也不再算作一手杀，因此不会再把这类点筛掉。

发布前再清理冲四拖延：白棋冲四仅有一个成五点、黑棋固定应手恰好挡住该点，且删去这两颗交换子后，整棵原后续策略仍能以完全相同的坐标、合法性、必要防点和结束位置重放获胜，才删除该白棋候选。改变杀法的冲四、必须挡住黑棋成五的点均保留；若全部选点都是同类拖延（包括唯一选点），省去白冲四、黑挡四两手，直接接上最短的已验证后续；连续出现时反复省略，直到稳定，保留后续有效防守菜单。当前 4,356 个父局面保存 8,509 项删枝证明，其中 1,947 项省去交换并接续棋谱。接续后的白棋局面已按普通局面重新筛选。已经随上层删除或改换历史的子树不再重复计数。该判断是保守的充分条件，不把“最后仍然输了”直接当作可删依据。J7 使用同一套冲四重放证明、删枝和接续规则。旧压缩谱的禁手与冲四证明继续离线验证。

冲四的价值判断在计数和引擎排序之前执行，由 `scripts/vcf-engine.mjs` 的 `pointlessFour` 完成。对非必须的白棋冲四，比较有无这组交换时每个空点的 VCF 结果，以下四种情况不再收录：黑棋挡点本身成五或形成成立的四三（`block-finishes`）；交换前黑棋没有 VCF、交换后有（`gives-black-vcf`）；别的点还能防住 VCF，但这个冲四之后所有点都防不住（`throws-away-defence`）；每个点在交换前后都防不住 VCF（`delay`）。白棋前后都活着、又看不出 VCF 层面收益的冲四继续保留，因为它可能在活三进攻层面有用，这里不算证明它无用。这些被排除的冲四不占九个名额，也不影响引擎评分带。菜单因此变空时，改用不是冲四的防点：优先引擎候选，其次按黑棋最短杀法长度和距离排序。点名请求的选点不受影响。排除的选点及原因记入覆盖文件的 `omittedFours`，`npm run verify:book` 逐项重算。

黑棋下一手有成立的四三或活四时，菜单必须覆盖每一个攻击点的直接防守，只有一个攻击点也一样；只挡活三而留下四三的菜单不再通过。只有白棋冲四才挡得住的攻击点不计入。直接防守指白棋落子后，某个攻击点不再成立，同时另一个攻击点仍能收束且白棋不能立即成五；收束手是活四时，继续记录白棋挡一端、黑棋成五。保留已有选点，先为每个未覆盖的攻击点加入一个防守，再补充其他直接挡点，总数不超过 9，名额不够时，由其攻击点已被其他选点覆盖的选点让位；优先占住攻击点及距离较近的防点。不会为了补侧翼而漏掉必须挡五的应手，也不会恢复无谓冲四。能完全挡住攻击的筛选存活点在展开时直接加入菜单并完整展开。

原路线由定式主线与离线引擎候选组成，连续冲四使用迭代加深搜索；发布时统一截断到首个四三或成五。所有保留的候选都验证到挑战结束点，没有中途断谱。覆盖范围是选定的白棋防守菜单，尚无全局最快或所有合法白棋应手的证明。未能闭合的新候选写入本地 `artifacts/g8-unresolved.json`，不进入线上菜单。

云月与雨月有盘端距离差异。本版采用云月实际坐标，没有把棋谱平移后声称雨月同样获胜。固定开局教学不实现比赛中的交换、五手打点及计时流程。

## 本地使用

需要 Node.js 22 或更高版本。

```sh
npm ci
npm run dev
```

打开 `http://127.0.0.1:5173`。本地服务器复用 Worker 的相同 API 处理代码。

```sh
npm test
npm run verify:book
node scripts/analyze-book.mjs
npm run build
npx wrangler deploy --dry-run
```

界面支持棋盘落子、固定黑棋应对、提示、手数开关、黑棋禁手标记、逐手复盘、悔棋、演示、JSON 导出、当前浏览器自动存档。键盘可用方向键移动焦点，回车或空格落子。

规则变更后修复已有棋谱，用 `--repair` 逐支运行 `scripts/expand-f10.mjs`：保留仍然合规的菜单和黑棋应手，只对变化的部分询问引擎，结果写入 `artifacts/<标签>-repair.json`。一本棋谱的所有分支修复后，运行 `node scripts/finish-repair.mjs --book=<棋谱>` 合并，再运行 `node scripts/prune-tempo-fours.mjs --book=<棋谱>`。G8 的四个分支 F10、F11、H9、H11 必须一起合并：只要有一支还停在旧规则的四三上，整本棋谱都过不了验证。新增走法展开超过 `REPAIR_BUDGET`（默认 1,500 个局面）仍未闭合时放弃该走法，并记入覆盖文件的 `unclosedMoves`。

## 部署

1. 在 `wrangler.jsonc` 中把 `ALLOWED_ORIGINS` 加入 GitHub Pages 的来源（只有协议和域名，不带仓库路径），例如 `https://YOUR_NAME.github.io`。
2. 登录 Cloudflare 并部署 API：

   ```sh
   npx wrangler login
   npm run deploy:api
   ```

3. 将仓库推到 GitHub，设置仓库 Actions 变量 `RENJU_API_BASE` 为输出的 HTTPS Worker 根地址。不要把任何 Cloudflare Token 写入前端。
4. 仓库 Settings → Pages → Source 选择 **GitHub Actions**。推送 `main` 或手动运行 `Deploy classroom to GitHub Pages` 工作流即可发布。

前端全部使用相对资源路径，兼容 `https://USER.github.io/REPO/`。缺少 API 地址时 CI 会明确失败，避免发布无法连接的课堂。

本项目无数据库、无账号系统、无服务器持久化对局；学习进度保存在浏览器 localStorage。清理浏览器数据会清除进度，可先导出棋谱。Worker 无需 D1/KV 或付费 AI 服务。

## 结构

- `public/`：原生 HTML/CSS/JS 教学界面。
- `src/renju.mjs`：禁手与成五判断；递归判断真实活三，四按子集去重；独立的挑战重放在首个黑棋四三结束。
- `src/book.mjs`：固定开局、主线、原创讲解与来源。
- `data/responses.json`：旧固定应对及压缩冲四证明，保留用于离线验证。
- `data/g8.json`：G8 挑战的完整有限策略树；白八 4 个选点，后续白棋 1–9 个选点，黑棋一个应手。
- `data/g8-runtime.json`：部署使用的紧凑后续节点图，相同后续共用节点；保留所有候选点、顺序、黑棋应手和距离。原始棋谱不随 Worker 装载。
- `data/f10-requests.json`：用户明确要求加入的 F10 防点及其完整局面，重建时保留。
- `data/f10-coverage.json`：F10 每个白棋局面的筛选记录，仅用于离线验证，不装入 Worker。
- `data/f11-coverage.json`、`data/h9-coverage.json`：F11、H9 使用相同规格的逐层筛选记录，仅用于离线验证。
- `data/double-four-three-coverage.json`：新增侧翼防点、所阻止的四三威胁及另一侧固定收束点，仅供离线验证。
- `data/tempo-four-pruning.json`：已移除冲四的固定挡点和原后续图，供独立重放比较；不装入 Worker。
- `data/j7.json`、`data/j7-runtime.json`：白6 J7 的完整候选树与部署用压缩节点图。
- `data/j7-coverage.json`、`data/j7-tempo-four-pruning.json`、`data/j7-double-four-three-coverage.json`：J7 的逐层筛选、冲四删除与两侧四三防守证据，仅供离线验证。
- `data/w6h9*.json`、`data/w6g9*.json`：白6 H9、G9 的完整树、压缩运行图和同规格筛选/删枝/补侧证明。白8 H9 仍使用原来的 `h9-coverage.json`，两者不会混用。
- `data/w4j8*.json`、`data/w4g8*.json`：白4 J8、G8 的独立完整树、压缩运行图和筛选/删枝/补侧证明。
- `src/opening-book.mjs`：连接白4 H7、J8、G8 三支；H7 下继续连接原有四个白6策略。原有后续节点、候选顺序和固定黑棋应手保持不变。
- `data/flower-w4h9*.json`、`data/flower-w4g7*.json`、`data/flower-w4h10*.json`：花月白4 H9、G7、H10 的原始树、紧凑运行图及筛选、删枝、补侧验证证据。
- `src/session.mjs`：棋谱遍历、合法性校验、复盘状态。
- `worker/index.mjs`：无状态 JSON API，限制请求大小并按来源配置 CORS。
- `scripts/tactics.mjs`、`generate-book.mjs`：仅离线生成冲四应对，线上不运行搜索。
- `scripts/verify-book.mjs`：验证全部棋谱转换及冲四证明。
- `scripts/build-g8.mjs`：离线生成 G8 候选树；`scripts/verify-g8.mjs` 验证每条路线在首个合法四三或成五处结束。
- `scripts/expand-f10.mjs`：递归扩展白八分支，默认 F10，传入 `--branch=F11` 或 `--branch=H9` 扩展相应分支；各分支独立缓存引擎分析和可恢复的生成进度。`scripts/f10-candidates.mjs` 定义三者共用的候选筛选，`scripts/verify-f10.mjs`、`scripts/verify-f11.mjs`、`scripts/verify-h9.mjs` 独立重查每层覆盖。
- `scripts/compact-g8.mjs`：生成紧凑运行时棋谱；测试逐个原始局面核对运行时所有选点和应手。
- `scripts/trim-books.mjs`：统一裁剪 G8 树和 J7 压缩分支，删除结束点后的节点，并重新统计路线；两种生成器发布时都会调用。
- `scripts/prune-tempo-fours.mjs`：反复清理不改变杀法的冲四直至稳定；`scripts/verify-tempo-fours.mjs` 重查每项删除依据、接续菜单及固定黑棋应手，并扫描全谱，确保没有遗漏符合该判据的冲四。
- `scripts/augment-double-four-three.mjs`：补齐四三威胁的各侧直接防守，清理脚本末尾自动调用；也可单独运行 `npm run complete:sides`。`scripts/verify-double-four-three.mjs` 逐个新增点重验并扫描全部白棋局面，检查是否仍漏掉另一侧；J7 的非冲四显式局面也一并检查。
- `.github/workflows/pages.yml`：测试、验证、构建、部署前端。

API：`GET /api/health`、`GET /api/lessons`、`POST /api/state`、`POST /api/move`。POST 输入为 `{history: ["H8", ...], lessonId: "opening", move: "G8"}`，`move` 仅落子时需要。默认课程为统一的 `opening`，旧 `main` / `j7` 接口仍可读取原独立棋谱。黑棋回合不传 `move`。

重建白6 H9 / G9 分别运行 `npm run expand:w6h9` / `npm run expand:w6g9`。两者沿用相同递归筛选、无谓冲四删除和四三两侧防守补齐规则；`node scripts/verify-white-six.mjs` 独立验证全部记录，且已纳入 CI 的 `verify:book`。

重建白4 J8 / G8 分别运行 `npm run expand:w4j8` / `npm run expand:w4g8`，中断后设置 `J8_RESUME=1` / `G8_RESUME=1` 继续同版本检查点。`node scripts/verify-white-four.mjs` 验证所有新路线、冲四删除证明、四三两侧覆盖和逐层候选筛选，已纳入 CI。新增白4路线由离线引擎提出并独立校验，不声称源自 H7 的参考图。

新增主线时修改 `src/book.mjs`，运行 `node scripts/generate-book.mjs`，随后运行测试和验证。每个黑棋节点只能有一个固定应手；白棋节点允许多个分支。未知分支必须明确保留为未收录。

重建 G8 树需将 [Rapfi 官方发行版 250615](https://github.com/dhbloo/rapfi/releases/tag/250615) 的 Windows SSE 引擎、配置与权重放入本地 `artifacts/rapfi/`（或设置 `RAPFI_DIR`），再运行 `npm run build:g8`。本仓库不分发引擎和权重，也不在线运行引擎；生成的落子数据和独立验证器已提交。CI 只验证已提交棋谱，不重新调用引擎。

白6 J7 使用 `npm run expand:j7` 独立重建；设置 `J7_RESUME=1` 可从同版本检查点继续。生成器复用相同候选筛选，随后执行同一冲四清理和四三两侧防守补齐。`scripts/verify-j7.mjs` 对 J7 全树分别验证终局、禁手、候选覆盖和删除依据。线上按 lessonId 选择独立节点图，J7 请求不能借用 G8 的历史。

单独扩展 F10 使用 `npm run expand:f10`，F11 使用 `npm run expand:f11`，H9 使用 `npm run expand:h9`；中断后分别设置 `F10_RESUME=1`、`F11_RESUME=1`、`H9_RESUME=1` 从同版本检查点继续。只有完整展开并通过棋谱验证后才覆盖正式数据。普通 `build:g8` 会保留已扩展的 F10、F11、H9 子树，避免其他分支新增选点时退回较小的旧谱。向 `data/f10-requests.json` 添加指定局面的防点后，可运行 `npm run add:f10`，只扩展新增防点的后续，再重新生成运行时数据和覆盖记录。上述生成命令都会在最后执行冲四清理，并同步更新三个分支的覆盖记录，避免重建时恢复冗余分支；也可单独运行 `npm run prune:book`。用户指定点同样服从后续明确要求的冲四清理规则。

## 棋谱与规则来源

- [励精连珠教室：云月白4 H7、黑5 G10](https://www.ljrenju.com/croom/i06/i06ba.htm)：本期两个主线的事实性落子坐标参考图 `i062111.gif`、`i062725.gif`。不包含该网站原图、原文或整套棋谱。
- [励精连珠教室：花月棋形](https://www.ljrenju.com/croom/d04/d04.htm)：核对前三手与对称强防。新增后续由离线引擎独立生成并校验，不复制站内图谱。
- [RIF 国际连珠规则](https://gomoku.renju.net/rifrules/)：第 9.1–9.3 条，黑三三、四四、长连及成五优先；白棋没有相应禁手。

讲解和界面均为本项目新写。收束变化由程序独立生成。验证覆盖落子合法性、真实活三、直接成五点，以及所有保留路线在首次四三或成五后停止；接口拒绝结束后继续落子。这里验证的是所录候选路线，不是所有白棋防守的穷尽证明。
